# Jonokotha (জনকথা)

**Your neighbourhood's problems, straight to your representative.**

Jonokotha is a Bangla-first, mobile-first, installable web app (PWA) that gives citizens in Bangladesh a simple, trackable way to tell their elected representative about local problems: roads, drains, water, power, waste. A citizen types, speaks or photographs a problem, an AI intake agent drafts the report, the citizen checks it and sends it, and from then on every step is public on a status timeline with a reference ID (for example `JK-2026-1001`). The MP's office gets a triaged queue instead of a flood of messages, with an AI summary, similar cases and a cited agency suggestion.

Built for the AIBC 2026 competition (Competition 1, CivicSphere AI). Live staging: <https://jonokotha.vercel.app>.

> **People decide, AI assists.** No AI output changes a case status, contacts an agency or reaches a citizen without explicit staff approval. See [AI](#ai-agents-and-where-they-stop).

## What it does

**For citizens** (no account needed to read; sign in to report, support or ask)

- Report by typing, speaking (browser speech-to-text) or photo, in Bangla, English or Banglish. Five steps, an emergency notice that points to 999, and a draft you always review.
- Public, trackable reports with reference IDs, status timeline, before-and-after photos and "I have this problem too" counts.
- Area view with filters and an approximate map (exact coordinates are never published).
- Ideas with support and arguments, polls, consultations, community priorities, participatory budgeting, project tracker, office commitments.
- Ask your MP privately or publicly; follow reports, areas and projects and get notifications (in-app, email, web push).
- Find your representative with the source and the date it was last checked.
- Bangla and English interface, installable PWA with an offline page, accessibility checks in CI.

**For MP offices and staff**

- Triaged inbox, case page with assignment, notes, status changes through an audited state machine, SLA timers.
- AI copilot (summary, missing information, Bangla reply draft, routing suggestion, duplicate candidates), always as a suggestion.
- Per-area roles: office manager, case officer, MP (view, analytics, approve), agency liaison. MP approval can be required for announcements, public replies and project changes.
- Analytics and KPIs from real statuses, announcements, polls, consultations, projects, commitments, exports.

**For agencies and admins**

- Agency liaison sees only what was referred to their agency (no reporter, no internal notes), with five audited actions.
- Moderators review reported content. Admins manage accounts, feature flags, categories, constituencies, integrations, audit log, AI runs and evaluations, and system health.

**Also built, behind feature flags** (all off by default, so an unfinished route never gets a link in production)

- Release 1.1: consultations, commitments, priorities (`NEXT_PUBLIC_FLAG_RELEASE11=1` switches them all on).
- Release 2: participatory budgeting, open data, RTI, MP records, assisted reporting for volunteers and regional admins (`NEXT_PUBLIC_FLAG_RELEASE2=1`).
- Dadu (জমির দাদু), a helper character that explains pages and answers questions, with optional voice (`NEXT_PUBLIC_FLAG_DADU=1`, `..._DADU_VOICE=1`). Details in [`docs/frontend.md`](docs/frontend.md).

## How a report travels

```
Citizen types / speaks / photographs
        │   PII (phone, email, ID numbers) is redacted before any model call
        ▼
Intake agent drafts title, category, description, area, urgency ──► citizen edits and submits
        ▼                                        (danger words force "urgent" and point to 999)
Issue is created with a reference ID, public timeline starts
        ▼
Office inbox ── AI copilot suggests summary, gaps, duplicates, agency (with source and date)
        ▼
Staff decide: assign, note, refer to agency, change status   (audited, state machine enforced in SQL)
        ▼
Citizen sees each step, gets notified, can give feedback
```

## AI agents and where they stop

Every agent goes through one `runAgent` wrapper: a forced tool call, Zod-validated output, a typed fallback, and a row in `ai_runs`. If the provider is down or returns something invalid, a keyword fallback takes over and the UI says the AI summary is off; the citizen can always just type.

| Agent | Output | Guard |
|---|---|---|
| Intake | Draft title, category, description, area hint, urgency | Citizen reviews and edits before sending |
| Office copilot | Summary, missing information, Bangla reply draft | Every claim must cite fact ids that exist, otherwise the rule-based fallback is used |
| Routing | Suggested agency | Retrieved from the sourced agency directory; shows source, URL and date checked; "no confident suggestion" below the threshold |
| Duplicate finder | Candidate duplicates with reasons | Scoped to office and category; marking a duplicate is a separate staff action |
| Insight | Short note on aggregate numbers | Dropped if it contains a number not in the statistics |
| Translation, transcription | Machine translation, speech-to-text | Labelled as machine output; typing always works |

Default model is `claude-opus-5-5` (`ANTHROPIC_MODEL`), called server-side through the Anthropic SDK; an Anthropic-compatible gateway can be set with `AI_BASE_URL`.

**Measured so far** (on 118 synthetic cases written by the team: 66 Bangla, 37 English, 15 Banglish; one run; small sample): the keyword fallback gets 61.0% category accuracy and 64.4% routing top-1; PII redaction recall is 10/10 with 0 false positives on 110 clean cases; the lexical duplicate baseline has precision 36.4% and recall 40.0%. Embedding duplicate quality has not been measured, and nothing here is a claim about field accuracy. Read the limitations first in [`docs/aibc/eval-results.md`](docs/aibc/eval-results.md) and [`docs/aibc/eval-baseline.md`](docs/aibc/eval-baseline.md). Reproduce with `npm run eval`.

## Architecture

One Next.js application (a modular monolith) on Supabase. The decision and the migration plan if it is ever split are in [`docs/architecture.md`](docs/architecture.md).

```
Browser / installed PWA                          Scheduled worker (cron)
   │ HTTPS, cookie session                           │ Bearer CRON_SECRET
   ▼                                                 ▼
 src/proxy.ts (session refresh, security headers)   /api/internal/{jobs,maintenance,notifications,...}
   ▼
 /api/v1/**  run(): auth, MFA gate, CSRF origin check, size + rate limits, idempotency, request id
   ▼
 service module: Zod validation, PII redaction, feature flags
   ├─► Postgres (user's JWT): RLS tables + SECURITY DEFINER functions (office_can, is_admin, audit_write, notify_user)
   ├─► Storage: private buckets for photos and video, signed URLs
   ├─► AI provider (server only): runAgent(), logged in ai_runs, manual fallback
   └─► Email / Web Push via the job runner, with retries and dead letters
```

The rule that holds it together: **the database decides.** Route handlers hold no business logic; services validate input and call an RLS-protected table or an audited SQL function; a service never trusts a role, constituency or reporter id from a request body.

## Getting started

Requirements: Node.js 22 or newer, npm. Docker only if you run the database tests.

```bash
npm install
cp .env.example .env.local   # then fill in the values below
npm run dev                  # http://localhost:3000
```

Minimum environment for a working app (names only; never commit `.env.local`):

| Variable | Used for |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Browser and server access under RLS |
| `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` | AI drafting and the office copilot (without a key, the keyword fallback is used) |
| `SUPABASE_SERVICE_ROLE_KEY` | Scripts and server jobs only; never `NEXT_PUBLIC_*` |
| `CRON_SECRET` | Scheduled jobs under `/api/internal/*` (16+ characters) |

Everything else (Sentry, alert webhook, CSP mode, Azure Speech for Dadu's voice, demo login) is optional and described in [`.env.example`](.env.example). Then:

```bash
npm run check:env      # reports set/missing for each variable and checks the AI endpoint, without printing keys
```

First-time Supabase setup, applying migrations in order, promoting a staff account and seeding the sample data are in [`docs/backend-setup.md`](docs/backend-setup.md). `supabase/migrations/` holds 48 migrations; apply them in order and run `npm run lint:migrations` after adding one.

Useful scripts:

| Command | What it does |
|---|---|
| `npm run build` / `npm start` | Production build and server |
| `npm run typecheck`, `npm run lint` | Types and ESLint |
| `npm run seed:demo` | Load the labelled sample constituency and cases (needs the service role key) |
| `npm run check:bundle` | Fails if a server secret reached a client bundle |
| `npm run check:release` | Release gate checks |
| `npm run audit:ui` | UI audit script |
| `npm run eval`, `npm run eval:gate` | AI evaluation and its regression gate |
| `npm run drill:restore`, `npm run backup:local` | Restore drill and local backup |

## Try it without a database: demo mode

Open `/demo` and press **Start the demo**. This sets a `jk_demo=1` cookie; the real screens then answer from fixtures in code (`src/lib/demo/`), nothing is read from or written to the database, votes and questions vanish on reload, and a banner stays on every page. Example references start with `JKD-` so they never look like real reports. The hub lists every feature with a "try this" link.

**One-click role logins (staging only).** With `DEMO_LOGIN=true` and `DEMO_PASSWORD` set on the server, `/login` shows buttons for citizen, office manager, case officer, MP, agency liaison and moderator. They sign in to real, pre-created accounts (`supabase/seed/demo_users.sql`), so RLS and office scopes still apply. There is deliberately no admin button. **Turn this off before real users or judging:** while it is on, anyone who reaches the site can become an MP or a moderator.

## Testing and quality gates

```bash
npm test                  # unit tests, no database (107 test files)
npm run test:e2e          # Playwright: mobile 375 px and desktop 1280 px, axe accessibility checks
npx supabase start && npx supabase db reset
npm run test:db           # schema, roles, RLS, state machine, API routes (refuses non-local URLs)
npm run test:rls          # only the RLS suite
npm run test:api          # only the API suite
```

Extra e2e suites run on their own servers and flags: `test:e2e:r11` (Release 1.1), `test:e2e:r2` (Release 2), `test:e2e:dadu` (Dadu), and `test:e2e:real` against a real local stack.

CI (`.github/workflows/ci.yml`) runs four jobs: **checks** (lint, migration lint, types, unit tests, build, bundle check, Playwright e2e), **database** (all DB, RLS and API tests on a local Supabase), **security** (secret scan, dependency audit) and **eval-gate** (the offline evaluation must not fall below its stated floors). A test fails the build if any table lacks row-level security or an RLS test.

## MCP servers

Jonokotha exposes its own tools to AI assistants over the Model Context Protocol (JSON-RPC over HTTP).

| Endpoint | Who | Tools |
|---|---|---|
| `POST /api/mcp` | Staff, with a Bearer access token; row-level security applies as that person; every call is audited | `search_cases`, `agency_directory`, `case_timeline`, `area_statistics` (read-only), `propose_note` (creates a pending suggestion only) |
| `POST /api/mcp/public` | Anyone, no sign-in; anonymous Supabase role, read-only, rate limited per IP, never uses the service-role key | `list_categories`, `agency_directory`, `helplines`, `search_public_cases`, `public_case_status` |

The public server can only return what a visitor to the website can already read: no reporter, no staff, no AI fields, no private case text.

## Security and privacy

- Identity comes only from the session. Roles are citizen, staff (per-area), moderator and admin; MFA (TOTP) enforcement is built for MP, moderator and admin and is switched by a flag.
- RLS on every table; privileged changes go through `SECURITY DEFINER` functions that check `office_can()` / `is_admin()` and write an append-only audit log, for everyone including the service role.
- Public data leaves only through views with explicit column lists. No reporter, voter, token or exact coordinate is in any view.
- Personal data (phone, email, ID numbers) is redacted before any model call and before storage. Notifications carry generic text only.
- Uploads: photos are re-encoded (metadata removed), video is type-checked by content with size and length limits and stored in private buckets.
- Demo data is flagged `is_demo` and labelled "নমুনা" (sample); no real person, MP or statistic is invented, and demo tools are refused in production.
- Secrets live in server environment variables only, enforced by `npm run check:bundle`.

Details: [`docs/security.md`](docs/security.md), [`docs/aibc/security-review.md`](docs/aibc/security-review.md), [`docs/aibc/pia.md`](docs/aibc/pia.md), [`docs/aibc/data-sovereignty.md`](docs/aibc/data-sovereignty.md), [`docs/permission-matrix.md`](docs/permission-matrix.md).

## Status and known limits

An honest list, mostly taken from [`docs/security.md`](docs/security.md) and the pilot documents:

- Per-IP rate limits are in memory per instance; a shared limiter is still open.
- No independent penetration test has happened yet (plan in `docs/aibc/pilot/pentest.md`).
- MFA enforcement is built but off until TOTP enrolment exists in the sign-in screens.
- No malware scanner is configured for uploads (photos are re-encoded, video is type-checked).
- AI quality is measured only on synthetic data (see above); embedding-based duplicate detection is unmeasured.
- Some office dashboard tiles show "needs backend data" until the matching data exists.
- Capacity is sized for tens of areas and thousands of public issues; PostGIS is not enabled.
- Sample data (constituency, agencies, demo cases) is labelled and is never sent to a real agency.
